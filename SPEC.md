# SPEC.md — NYCU Library MCP Wrapper

Technical design document. See [README.md](./README.md) for a high-level overview and [INSTALL.md](./INSTALL.md) for deployment steps.

## 1. Background

[NYCU Library](https://www.lib.nycu.edu.tw/) exposes an official MCP (Model Context Protocol) server at `https://mcp.lib.nycu.edu.tw/`, documented for direct use with Claude and ChatGPT. It authenticates end users via OAuth 2.1 against their own NYCU SSO credentials and exposes catalog search and personal account (loans/holds/purchase requests) tools.

The upstream server returns rich, UI-oriented structured payloads — e.g. a `viewType: "catalog"` result carrying a list of book records with per-campus availability, or an account dashboard result. These are designed for clients that can render bespoke cards from `structuredContent`. The problem this project solves: **card rendering and model-visible content are two separate concerns**, and not every MCP client guarantees the model itself sees full item-level detail.

Concretely:
- Some clients render `structuredContent` into a native UI card, but the model's own context window may still only receive a short summary string from the tool result's `content` field (e.g. `Displaying 10 catalog item(s).`).
- Other clients (e.g. Open WebUI, as of the version this project was built against) have no special rendering for this `viewType` convention at all — the user sees nothing informative, and the model sees only the same short summary.

Either way, the underlying data (titles, authors, availability, call numbers) risks being present in the payload but invisible to whichever party actually needs it to answer the user's question.

This project is an independent, unofficial wrapper. It is not affiliated with, endorsed by, or sponsored by National Yang Ming Chiao Tung University (陽明交通大學) or its Library.

## 2. Goals

- Guarantee that both `search` and `fetch` tool results carry complete, item-level information in the `content` field, in Markdown, regardless of which downstream MCP client is consuming them.
- Preserve the original upstream `structuredContent` payload unmodified, so clients capable of richer rendering can still use it.
- Handle the full two-legged OAuth 2.1 handshake transparently, so the end user only ever sees a single NYCU SSO login prompt per session/token lifetime.
- Run entirely on Cloudflare's free tier with no server to operate or patch.
- Remain a thin, auditable proxy — no caching of catalog data beyond a single request/response cycle, no analytics, no logging of credentials or personal borrowing data.

### 2.1 Non-goals

- This wrapper does not attempt to add features the upstream server doesn't have (e.g. it does not implement checkout/renewal actions if the upstream API doesn't expose them).
- It does not attempt to work around the upstream's ~3-day access token lifetime; there is no refresh-token grant offered by NYCU Library's authorization server, so re-authentication is expected and treated as normal behavior, not an error state to suppress.
- It does not attempt to be a general-purpose OAuth proxy for arbitrary upstream MCP servers — the normalization logic in `mcp-server.ts` is written against this specific upstream's response shapes.

## 3. Architecture

```
Any MCP-compatible AI workspace (Open WebUI / Claude / ChatGPT / etc.)
        │  OAuth 2.1 (Dynamic Client Registration + PKCE)
        │  MCP over Streamable HTTP
        ▼
┌───────────────────────────────┐
│  Cloudflare Worker (this repo)│
│  - OAuth 2.1 provider layer   │
│  - OAuth 2.1 client layer     │
│  - stateless MCP handler      │
│  - response normalizer        │
└───────────────────────────────┘
        │  OAuth 2.1 (DCR + PKCE)
        │  MCP over Streamable HTTP
        ▼
   mcp.lib.nycu.edu.tw
   (NYCU Library's official MCP server)
```

The Worker plays two independent OAuth roles simultaneously:

1. **Provider**, towards the downstream AI workspace — implemented with [`@cloudflare/workers-oauth-provider`](https://github.com/cloudflare/workers-oauth-provider). This is what lets Open WebUI, Claude, ChatGPT, etc. register themselves as OAuth clients of the Worker and obtain their own access tokens for calling `/mcp`.
2. **Client**, towards NYCU Library's authorization server — the Worker itself performs Dynamic Client Registration against `mcp.lib.nycu.edu.tw`, then does the standard PKCE authorization-code flow on the end user's behalf when they first authenticate.

These two token exchanges are fully decoupled. The downstream AI workspace only ever holds a Worker-issued token; it never sees the NYCU access token. The NYCU access token lives exclusively in Workers KV, keyed by an internal `grantId` generated by the OAuth provider layer.

### 3.1 Request lifecycle

1. AI workspace calls `initialize` on `/mcp` → Worker's MCP handler responds and issues an `Mcp-Session-Id`.
2. AI workspace calls `tools/call` (`search` or `fetch`) with that session ID.
3. The Worker's OAuth provider middleware resolves the caller's `grantId` from the Worker-issued access token, looks up the corresponding NYCU access token in KV.
4. If missing or expired, the tool returns a structured "please re-authenticate" error (see §8) rather than a raw HTTP error, so it renders sensibly in chat.
5. Otherwise, the Worker performs its own `initialize` handshake with `mcp.lib.nycu.edu.tw` (or reuses a cached upstream session, depending on implementation state — see `src/mcp-server.ts`), then forwards the equivalent `tools/call`.
6. The upstream's raw JSON-RPC/SSE response is parsed (see §7), normalized into `content` + `structuredContent`, and returned to the AI workspace.

### 3.2 Statelessness

Tool calls are served via [`agents/mcp`](https://github.com/cloudflare/agents)'s `createMcpHandler`, not the older `McpAgent` Durable Object pattern. This means:
- No Durable Object binding is required in `wrangler.jsonc`.
- Each request is handled independently by whichever Worker isolate picks it up; the only shared state is what's persisted in KV (tokens, DCR client IDs, OAuth grants/sessions).
- This keeps the Worker within the free tier (no Durable Object billing) and simplifies reasoning about concurrency.

## 4. Security Model

- **No static secrets.** Both OAuth legs use Dynamic Client Registration + PKCE. There is no client secret to provision, store, or rotate anywhere in this codebase.
- **`wrangler.jsonc` is safe to commit.** It only contains a KV namespace ID and a Cloudflare account ID — both are identifiers, not credentials. Knowing them does not grant access to anything; an attacker would still need a valid Cloudflare API token or account session to act on them.
- **NYCU access tokens are opaque to the downstream AI workspace.** They are stored in Workers KV under a key scoped to the internal `grantId` issued by the Worker's own OAuth provider layer, and are never included in logs, error messages, or tool responses.
- **No credential storage.** The Worker never sees or stores the user's NYCU SSO username/password — authentication happens entirely on NYCU's own login page during the OAuth redirect; the Worker only ever receives an authorization code, then an access token.
- **`fetch_account_page` is intentionally unwrapped.** This upstream tool is a pagination helper whose own description states it is "not intended for model use." Wrapping it would risk exposing an internal implementation detail as if it were a supported public tool.
- **Blast radius of a leaked Cloudflare API token** is the Worker's own deployment and KV namespace — not NYCU's systems. A leaked Worker-hosted NYCU access token would expose that one user's own library account (their own loans/holds) for up to ~3 days, scoped to whatever the upstream API itself allows.
- Anyone deploying this for users other than themselves should review NYCU Library's own terms of use for the MCP service (see §10) and this section before doing so.

## 5. Tools

### 5.1 `search`

Wraps the upstream catalog search tool.

**Input parameters:**

| Parameter | Type | Description |
|---|---|---|
| `query` | string | Search terms (title, author, keyword). |
| `offset` | integer, optional | Pagination offset into the result set. |
| `resource_type` | string, optional | Filter by resource type (e.g. book, journal, thesis) as exposed by upstream. |
| `access` | string, optional | Filter by access type (e.g. physical, electronic) as exposed by upstream. |
| `scope` | string, optional | Search scope as exposed by upstream (e.g. catalog-wide vs. a specific collection). |
| `sort` | string, optional | Sort order as exposed by upstream. |
| `max` | integer, optional | Caps how many results are rendered into `content` for this call, independent of how many the upstream returned — protects against extremely long chat messages. |

**Output:** see §6.

### 5.2 `fetch`

Wraps the upstream account-dashboard tool: current loans, active holds, and purchase requests for the authenticated user.

**Input parameters:** none beyond the caller's own authenticated session — the upstream tool is scoped entirely to "my account," there is no target user parameter.

**Output:** see §6.

## 6. Response Normalization

Every tool response returned to the downstream AI workspace has this shape:

```json
{
  "content": [{ "type": "text", "text": "<Markdown, always item-level>" }],
  "structuredContent": {
    "summary": "<one-line summary, same string upstream would have used>",
    "viewType": "catalog | account | ...",
    "normalized_data": [ /* wrapper's own parsed array of items */ ],
    "model_content": "<same text as content[0].text, duplicated for clients that read structuredContent directly>",
    "original_payload": { /* untouched upstream structuredContent, verbatim */ }
  }
}
```

Design rule: **`content` must never degrade to a bare summary line.** This is the field every MCP client is contractually obligated to surface to the model (`structuredContent` is optional/client-dependent per the MCP spec), so it is the only field this wrapper treats as load-bearing for model visibility. Everything else is a convenience for clients that want it.

For `search`, `content` renders each result as a short block: title, author(s), resource type, per-campus/per-branch availability, call number, and a permalink if the upstream provided one — up to the `max` parameter (default chosen to stay well under typical context/message-length limits, currently in the same order of magnitude as the upstream default page size).

For `fetch`, `content` renders each loan/hold/purchase-request as a line with title, due date or status, and renewal/cancellation eligibility if the upstream includes it.

## 7. Upstream Transport Details

The upstream (`mcp.lib.nycu.edu.tw`) is a standard MCP server over Streamable HTTP, with a few practical details that the Worker must handle explicitly:

- **Session handshake is mandatory.** Every `tools/call` must be preceded by an `initialize` call, and must carry the `Mcp-Session-Id` returned from it. Calling `tools/call` cold returns `400 Bad Request: Missing session ID`.
- **Content negotiation is strict.** Requests must send `Accept: application/json, text/event-stream` — omitting either value returns `406 Not Acceptable`.
- **Responses may be SSE, not plain JSON.** The upstream may reply with a `text/event-stream` body (`event: message` / `data: {...}` framing) rather than a bare JSON body, even for what is logically a single request/response exchange. The Worker's `readMcpResponse()` helper (in `src/mcp-server.ts`) parses both shapes transparently; naively calling `response.json()` will throw on the SSE form.

## 8. Token & Session Lifecycle

KV is used for two independent purposes, effectively partitioned by key prefix:

| Key pattern | Purpose | Lifetime |
|---|---|---|
| `nycu_dcr_client_id` | Cached `client_id` from the Worker's own DCR registration against NYCU's authorization server. | Indefinite until manually deleted (e.g. when moving from local dev to production redirect URIs — see INSTALL.md §6). |
| `nycu_token:<grantId>` | The end user's NYCU access token, scoped to the Worker-issued OAuth grant. | Matches the upstream token's own lifetime, currently **~3 days**, no refresh grant available. |
| `session:<id>` / PKCE-related keys | Transient state for in-flight OAuth handshakes (both legs). | Short TTL, auto-expires via KV's native TTL support. |

When a tool call finds an expired or missing NYCU token, it returns a clear, structured error message rather than letting the raw upstream `401` propagate — this is what triggers the downstream AI workspace's own OAuth flow to prompt the user to log in again. This is expected, routine behavior given NYCU's token policy, not a failure mode to work around.

## 9. Known Limitations

- No automated test suite; correctness has been validated manually via [MCP Inspector](https://github.com/modelcontextprotocol/inspector) against both the local dev server and the deployed Worker.
- `fetch_account_page` is not exposed (see §4).
- The response-normalization logic is written specifically against the current shape of NYCU Library's `viewType: "catalog"` and account-dashboard payloads; if NYCU changes their upstream schema, the normalizer will need corresponding updates.
- No refresh-token support is possible on this wrapper's side, since NYCU's authorization server does not issue refresh tokens for this service.
- Deployment and connection instructions are written with Open WebUI as the primary worked example; other MCP clients are expected to work via the same standard protocol, but haven't all been individually verified.

## 10. Compliance Notes

This wrapper authenticates strictly as the end user, using that user's own NYCU SSO credentials via the standard OAuth 2.1 flow — it does not scrape, bypass authentication, or access any data the user couldn't otherwise access by logging into the official service directly.

At the time of writing, NYCU Library's MCP landing page (`https://mcp.lib.nycu.edu.tw/`) documents official connection steps for Claude and ChatGPT and does not publish a separate terms-of-service page restricting third-party or custom MCP clients. The service is built on OAuth 2.1 Dynamic Client Registration, which by design allows any spec-compliant client — including this wrapper — to register itself; NYCU's FAQ on that page also confirms that multiple platforms can be authenticated independently and concurrently under the same account, which is the same relationship this wrapper has with the upstream service.

That said, this is not legal advice, and NYCU Library's own policies may change. Anyone deploying this wrapper for others (rather than personal use) should:
- Re-check `https://mcp.lib.nycu.edu.tw/` for any updated terms before publishing or sharing a deployment.
- Avoid implying official endorsement — see the disclaimer in [README.md](./README.md) and the NOTICE section of [LICENSE](./LICENSE).
- Consider notifying NYCU Library via the feedback/contact channel linked on their MCP page, since the page explicitly invites feedback on how the service is used.
